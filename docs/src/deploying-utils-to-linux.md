# Deploying the utils tools to a Linux box

The question this document answers:

> The scripts in `utils/bin` rely on the Gradle build folder. To run them on a
> Linux box, how should the scripts and jars be packaged — a container image, or
> something else?

The short answer: **something else — the Gradle distribution tarball the build
already produces.** A container is the right shape for the AMPS *server* (this
repo runs it that way), but for operator CLI tools that read and write local
files it adds friction without adding value, unless your estate is
container-only. The analysis below is the reasoning; the decision matrix at the
end is the summary.

## What actually has to travel

The tools are one Java dispatcher behind five thin wrappers:

```
utils/bin/fileToAMPS.sh ─┐
utils/bin/ampsToFile*.sh ├─ source _launch.sh ──> utils/build/install/amps-utils/bin/amps-utils
utils/bin/truncateAMPS.sh┘        │                        │
                                  │                        └─ start script + lib/*.jar
                                  └─ rebuilds via ./gradlew when sources are newer
```

Separate the development conveniences from the runtime:

| piece | role | needed on the Linux box? |
| --- | --- | --- |
| `lib/*.jar` (utils, common, amps-client, protobuf, gson, slf4j) | the program | **yes** |
| `bin/amps-utils` start script (generated by Gradle) | classpath + JVM launch | **yes** |
| a Java 21 runtime | executes it | **yes** (or bundled — see Option C) |
| `AMPS_HOST` / `AMPS_PORT` env vars | configuration | **yes** — the only config there is |
| `utils/bin/*.sh` wrappers | operator ergonomics | nice to have |
| `_launch.sh`'s gradle rebuild-if-stale | dev loop | **no** |
| the repository, Gradle, Maven Central access | building | **no** |

The load-bearing fact: the `application` plugin in
[`utils/build.gradle.kts`](../../utils/build.gradle.kts) already assembles a
**relocatable, self-contained directory** — `bin/amps-utils` plus every jar —
and provides `distTar`/`distZip` for free. The build-folder coupling is not in
the program at all; it lives entirely in `_launch.sh`'s dev-time lookup path.
Packaging is therefore mostly a matter of shipping what already exists.

One behavioural note when running the installed launcher directly: relative
`--file`/`--out` paths resolve against **the operator's current directory**
(the `workingDir = rootProject.projectDir` indirection only applies to
`./gradlew :utils:run`). On a deployed box that is exactly what an operator
expects.

## Option A — the Gradle distribution tarball (recommended)

```bash
# build machine (or CI)
./gradlew :utils:distTar
ls utils/build/distributions/          # amps-utils-1.0.0.tar

# target box
scp utils/build/distributions/amps-utils-1.0.0.tar box:/tmp/
ssh box 'mkdir -p /opt/amps-utils && tar -xf /tmp/amps-utils-1.0.0.tar -C /opt/amps-utils'

# run — works today, with no repo, no Gradle, no network
export AMPS_HOST=amps-prod-1 AMPS_PORT=9007
/opt/amps-utils/amps-utils-1.0.0/bin/amps-utils sow-to-file --topic orders --out /tmp/orders.json
```

The subcommand form (`sow-to-file`, `file-to-amps`, `txlog-to-file`,
`truncate`) is fully usable from the deployed tree **as-is**. The `*.sh`
convenience wrappers need the small follow-up change at the bottom of this
document to travel along; until then they are a repo-checkout convenience.

**Why this is the default:**

- **Zero new build machinery.** `distTar` comes from the `application` plugin
  the module already applies; nothing is added, so nothing new can break.
- **Transparent.** The artifact is a directory of jars and a shell script —
  inspectable, diffable, `jar tf`-able. When something goes wrong on the box at
  2am, that matters.
- **Small.** ~10 MB: the AMPS client, protobuf, gson, slf4j and this repo's two
  jars.
- **Trivial versioning and rollback.** The tar unpacks to a versioned directory
  (`amps-utils-1.0.0/`); point a symlink (`/opt/amps-utils/current`) at the
  live one and rollback is re-pointing it.
- **Works everywhere Java 21 does** — bare metal, VM, any distro, no root
  needed beyond the install directory.

**The one requirement:** a Java 21 runtime on the box (`java -version`). A JRE
is enough; the start script honours `JAVA_HOME` and falls back to `java` on the
`PATH`. If your boxes are managed, `temurin-21-jre` from your package channel
is the usual answer.

## Option B — fat/shadow jar

One merged jar via the Shadow plugin, run as `java -jar amps-utils.jar`.

Verdict: **not recommended here.** It adds a third-party plugin and the
jar-merging class of problems (service-file and `META-INF` collisions —
protobuf and gson are well-behaved, but you now own verifying that on every
dependency bump) to solve a problem Option A does not have: the dist is already
a single artifact — a tar. The only scenario where a fat jar genuinely wins is
"I may only copy exactly one file and cannot untar", which is rare enough to
not design for.

## Option C — self-contained runtime (jlink/jpackage)

Bundle a trimmed JRE with the app so the box needs **no Java at all**.
`jpackage --type app-image` over the Option A dist is the low-effort route
(the deps are non-modular, so full `jlink` needs a `jdeps` analysis first).

Verdict: the right choice **only** when target boxes cannot have Java 21
installed (locked-down images, no package channel). Costs: the artifact grows
to ~60–90 MB, and you now ship JRE security updates yourself — every JVM CVE
becomes a redeploy of your artifact rather than a package upgrade the platform
team already does.

## Option D — container image

```dockerfile
FROM docker.io/eclipse-temurin:21-jre
COPY utils/build/install/amps-utils /opt/amps-utils
ENTRYPOINT ["/opt/amps-utils/bin/amps-utils"]
```

```bash
podman run --rm --network host \
    -e AMPS_HOST=amps-prod-1 -e AMPS_PORT=9007 \
    -v /data/dumps:/out:z \
    amps-utils:1.0.0 sow-to-file --topic orders --out /out/orders.json
```

Verdict: **right when the estate is container-only; friction otherwise.** The
image itself is easy (twelve lines, above). The friction is inherent to
containerising a *file-oriented CLI tool*:

- every `--file`/`--out` path needs a volume mount, and the operator must keep
  container paths and host paths straight;
- output files land owned by the container UID unless you map users;
- reaching AMPS needs `--network host` or explicit publishing;
- "run a quick dump" becomes a podman incantation.

Contrast the AMPS **server** in this repo, which is rightly a container: it is
a long-running daemon with its own state directory, and the isolation is the
point. The utils are the opposite shape — short-lived, host-file-touching,
operator-driven. Same technology, opposite fit. Choose D if your Linux boxes
run *only* containers, or if the tools later grow into long-running services
(a scheduled dumper, for instance) — at which point the calculus genuinely
flips.

## Option E — OS package (rpm/deb)

Wrap Option A in an rpm/deb (nebula-ospackage Gradle plugin, or `fpm` over the
dist directory), declare a dependency on your Java 21 package, deliver through
the fleet's yum/apt channel.

Verdict: the **operationally best** endpoint for a managed fleet — versioning,
rollback and the Java dependency all ride existing infrastructure — but only
worth it if that infrastructure already exists. It is Option A plus packaging
ceremony; adopt it when the tools stop being a two-box affair.

## Decision matrix

| your situation | package as |
| --- | --- |
| box has (or can get) Java 21 — the common case | **A: distTar** |
| several boxes, existing yum/apt infrastructure | **E: rpm/deb wrapping A** |
| box cannot have Java installed | **C: jpackage app-image** |
| estate runs containers only / tools becoming services | **D: container of A** |
| "I can only copy one file, ever" | B: shadow jar (grudgingly) |

Every row except B literally contains Option A inside it, which is the real
conclusion: **build the dist; choose how to deliver it per environment.**

## Follow-up implementation checklist

Small changes, in the repo, to make Option A first-class (the doc above is
accurate today; this makes it convenient):

1. **Ship the operator wrappers in the dist.** In `utils/build.gradle.kts`:

   ```kotlin
   distributions {
       main {
           contents {
               from("bin") { into("bin"); filePermissions { unix("rwxr-xr-x") } }
           }
       }
   }
   ```

2. **Make `_launch.sh` dual-mode.** If `${BIN_DIR}/../lib` exists (deployed
   tree), exec `${BIN_DIR}/amps-utils` directly and skip the gradle
   rebuild-if-stale entirely; otherwise keep today's repo-checkout behaviour
   unchanged.

3. **Stamp a `VERSION` file** into the dist (`project.version` + git short
   SHA), so a box can answer "what build is this?" without guessing from jar
   names.

4. **Verify on a clean directory** — the deployment test is precisely the
   absence of the repo:

   ```bash
   ./gradlew :utils:distTar
   tar -xf utils/build/distributions/amps-utils-*.tar -C /tmp/deploy-test
   cd /tmp/deploy-test/amps-utils-*      # note: NOT the repo
   AMPS_HOST=localhost bin/amps-utils sow-to-file --topic orders --out /tmp/o.json
   bin/fileToAMPS.sh --topic desk.backup --file /tmp/o.json   # wrappers, post-change
   ```

5. Optional, per the matrix: a `utils/Containerfile` (the twelve lines above)
   and/or nebula-ospackage wiring — add when an environment in the matrix
   actually calls for it, not before.
